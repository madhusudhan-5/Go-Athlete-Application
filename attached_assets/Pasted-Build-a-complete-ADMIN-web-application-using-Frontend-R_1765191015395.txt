Build a complete ADMIN web application using:

Frontend: React (web, responsive)
Backend: Django REST Framework
Design System: Material Design 3 (MD3)
Color palette:
  primary: #0A1F35
  secondary: #DA6F2B
  darkPrimary: #030929
  use MD3 greys, black, white for surfaces
Light + Dark mode (user-toggle in settings), persist preference
Responsive for desktop / tablet / mobile

The ADMIN app sits BETWEEN Vendor app and Super Admin:
- SUPER ADMIN is highest and can manage Admins + global platform
- ADMIN manages Vendors, KYC, commissions, offers, promotions, bookings oversight, memberships, payouts, tickets, reports, analytics
- Vendor uses Vendor App only

========================================
AUTH & ROLES (ADMIN)
========================================
Backend:
- Use Django + DRF with token/JWT auth
- Admin user model (AdminUser) linked to Django User with:
  can_manage_vendors (bool)
  can_manage_commissions (bool)
  can_manage_offers (bool)
  can_manage_bookings (bool)
  can_manage_tickets (bool)
  can_manage_reports (bool)
  can_manage_memberships (bool)
  can_manage_payouts (bool)

Frontend:
- Login page at /admin/login
  Fields: email, password
  Validations: required, email format
  POST /api/admin/auth/login/
  On success: store token, load /admin/dashboard
- Protect all /admin/* routes, redirect unauthenticated to /admin/login

========================================
VENDOR MANAGEMENT
========================================
Route: /admin/vendors, /admin/vendors/:id

Backend models (brief):
Vendor:
  id
  first_name
  last_name
  owner_name
  business_name
  roles (array: VENUE, COACH, ECOM)
  email
  phone
  address
  city
  state
  pincode
  id_proofs (list of URLs, at least 2)
  license_docs (list of URLs)
  status (PENDING, APPROVED, REJECTED, SUSPENDED)
  rejection_reason
  created_at
  updated_at

Endpoints:
- GET /api/admin/vendors/?status=&role=&search=
- GET /api/admin/vendors/:id/
- POST /api/admin/vendors/:id/approve/
- POST /api/admin/vendors/:id/reject/ (payload: {reason})
- POST /api/admin/vendors/:id/suspend/ (payload: {reason})
- POST /api/admin/vendors/:id/activate/

Validation:
- Approve only if status=PENDING or REJECTED
- Reject requires reason with min length 10
- Suspend requires reason

Frontend:
- Vendor list with filters:
  status chips (ALL, PENDING, APPROVED, REJECTED, SUSPENDED)
  role filters (VENUE, COACH, ECOM)
  search by name/email/phone
- Vendor row shows:
  business name, roles, city, status badge
- Click row → Vendor Detail:
  basic info
  roles
  docs preview (id_proofs, license_docs)
  quick summary: venues, courts, products, coaches, bookings, revenue, commission paid
  action buttons: Approve, Reject, Suspend, Activate
- Use MD3 dialogs for Reject/Suspend to capture reason
- Show success toasts and update UI state

COMMISSION CONFIG (CRITICAL)
========================================
Admin configures commission for:
- court_bookings_commission_pct
- coaching_commission_pct
- ecommerce_commission_pct
- membership_commission_pct

Model:
CommissionConfig:
  court_pct (0–100)
  coach_pct (0–100)
  ecommerce_pct (0–100)
  membership_pct (0–100)
  effective_from
  created_by (AdminUser)

Endpoint:
- GET /api/admin/commission-config/
- PATCH /api/admin/commission-config/

Validation:
- 0 <= pct <= 100

UI:
- Route: /admin/settings/commissions
- MD3 form with sliders/number inputs
- Show preview of vendor earnings vs commission on sample values
- Save → success toast

========================================
OFFERS & PROMOTIONS MANAGEMENT
========================================
Admin defines offers that VENDORS can only select (not edit):

Model:
Offer:
  name
  description
  discount_type (PERCENT, FLAT)
  value
  max_discount_amount (optional)
  target_type (VENUE, COURT, PRODUCT, COACH, MEMBERSHIP)
  status (DRAFT, ACTIVE, EXPIRED)
  valid_from
  valid_to

Endpoints:
- GET /api/admin/offers/?status=
- POST /api/admin/offers/
- GET /api/admin/offers/:id/
- PATCH /api/admin/offers/:id/
- POST /api/admin/offers/:id/activate/
- POST /api/admin/offers/:id/deactivate/

UI:
- /admin/offers
  list offers with filters
  MD3 cards with status chips
  "Create Offer" button → form in dialog or separate page
- Validations:
  value > 0
  if discount_type=PERCENT then value <= 100
  valid_to > valid_from

Promotions:
- Admin-level promotions (higher-level campaigns)
Similar structure, with ability to attach offers to campaigns (optional).

========================================
BOOKINGS OVERSIGHT
========================================
Models use Vendor’s booking data; Admin only oversees.

Endpoints:
- GET /api/admin/bookings/?date=&vendor_id=&venue_id=&status=
- GET /api/admin/bookings/:id/
- PATCH /api/admin/bookings/:id/ (change status: CONFIRMED, CANCELLED, COMPLETED, NO_SHOW)
- POST /api/admin/bookings/:id/refund/ (payload: amount, reason)

Validations:
- Cannot cancel if already COMPLETED unless “force flag” (optional)
- Refund amount <= booking price

UI:
- Route: /admin/bookings
  filters:
    date range
    vendor
    status chips
  MD3 table list
- /admin/bookings/:id
  show:
    vendor, venue, court, timeslot
    customer name/phone
    price, commission, vendor earning
    membership info if applicable
  actions:
    change status (with reason where needed)
    trigger refund
  Confirmation dialogs for critical actions
